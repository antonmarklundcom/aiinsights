# O3 — Auth: shared password, signed cookie, proxy

## Built
- `src/lib/auth.ts`: `signSession` / `verifySession` over HMAC-SHA256 of `expiresAt` with
  `AUTH_COOKIE_SECRET`, 30-day cookie value `<expiresAt>.<hmac>`, Web Crypto only.
- `constantTimeEqual` hashes both sides before comparing, so neither the contents nor the
  length of a password guess is visible in the response time. `passwordMatches` wraps it.
- `hasSession()` / `requireSession()` read the cookie via `next/headers` behind a dynamic
  import, so the proxy bundle never pulls it in. `sessionCookieOptions()` is shared by
  login and logout: httpOnly, `secure` in production, `sameSite=lax`, path `/`.
- `src/proxy.ts`: 302 to `/login?next=…` unless the path is exempt (`/login`,
  `/api/telegram/*`, `/api/cron/*`, `/_next/*`, `/favicon.ico`) or the cookie verifies.
  `isExempt` is exported so the rules are unit-tested rather than read off a regex.
- `src/app/login/`: server-rendered page, client `LoginForm` on `useActionState`, and
  `login` / `logout` actions. Wrong password → 500 ms delay, then an inline error.
  `safeNext` keeps `next` a same-origin path (no `//evil`, no `/\evil`).
- `src/lib/actions.ts`: every action now starts with `await requireSession()`.
- `src/app/layout.tsx`: header with a "Log out" form, rendered only when signed in.
- `src/lib/auth.test.ts` (18) and `src/proxy.test.ts` (10): sign/verify happy path, tampered
  expiry, tampered signature, wrong secret, expiry boundary, malformed values, password
  compare, the production env rules, the matcher, and the exempt paths.

## Decisions
- **302, not 307.** `NextResponse.redirect` defaults to 307, which would replay an
  unauthenticated server action's POST body against `/login`. Plan §5.3 asks for 302 anyway.
- **Env is read from `process.env`, not `src/lib/env.ts`.** Touching `env` validates the
  whole set and throws on e.g. a missing `DATABASE_URL`; that must never take the proxy down
  (§4.5). `env.ts` still lists both keys as production-required, so production fails closed
  at startup, and `sessionSecret()` throws in production when the key is missing.
- **`AUTH_COOKIE_SECRET` has a constant development fallback.** Unreachable in production.
  Without it, a local checkout with a `DASHBOARD_PASSWORD` but no cookie secret could not
  log in at all — §4.5 says missing env degrades, not blocks.
- **The matcher is wide; the exemptions live in code.** A matcher has to be a build-time
  constant, `_next/data` reaches the proxy even when excluded, and a server action is a POST
  to the page it lives on — so a matcher that skips a path silently skips its actions too.
  The matcher only drops `_next/static`, `_next/image` and `favicon.ico`.
- **Exempting `/_next/*` does not leak page data.** App Router prefetches are RSC requests
  to the page's own path (`RSC: 1`), which the proxy still sees; `/_next/data/*` is a Pages
  Router convention this app has no routes for.
- The matcher test calls `unstable_doesMiddlewareMatch`; the proxy doc names it
  `unstable_doesProxyMatch`, but 16.3.3 still exports the middleware spelling.

## Known issues
- A non-exempt `/api/*` route added later gets a 302 to `/login` rather than a 401. Plan
  §5.3 says "redirect for every path except …", so this follows the contract; S4 should call
  `requireSession()` in any API route it adds and decide its own status code.
- `requireSession()` throws a plain `Error`, which React surfaces as a generic server-action
  failure. Enough for a single-user app; a redirect would need a client-side handler.
- The root layout reads the cookie, so every route is dynamic. Everything here is already
  `force-dynamic`, so nothing is lost, but S1 cannot statically render a page under it.
- In development with no `DASHBOARD_PASSWORD`, `hasSession()` is true, so the header shows a
  "Log out" button that just bounces through `/login`. Cosmetic, dev-only.
- The proxy's "dashboard is open" warning is de-duplicated by a module-global, which the
  proxy docs advise against relying on. Worst case it warns more than once.
- `README.md` is O1's file, so the login flow is documented here and in `.env.example` only.

## Vercel environment variables Anton must set
- `DASHBOARD_PASSWORD` — the single password for the dashboard. Production refuses to boot
  without it; there is no reset flow, so store it in a password manager.
- `AUTH_COOKIE_SECRET` — `openssl rand -hex 32`. Changing it logs the session out.
Both are already in `.env.example`. Set them on Production **and** Preview, or preview
deployments crash on first request.
