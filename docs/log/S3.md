# S3 — Screenshots: Telegram photo capture, Claude vision

## Built
- `src/lib/telegram-files.ts`: `selectPhotoSize` (largest `message.photo` entry ≤1,600px,
  falls back to the smallest if every size is over) and `downloadTelegramPhoto` (`getFile`
  → download → base64, media type read from the file extension).
- `src/lib/vision.ts`: `buildScreenshotImageBlock` shapes a downloaded screenshot into the
  Claude image content block; `SCREENSHOT_INSTRUCTION` is the read-the-on-screen-text prompt.
- `summarize.ts` (S3 block): when `imageFileId` is set, the image block goes in before the
  text block in the user turn (image fetched at summarize time, never stored); plain-string
  content otherwise, unchanged from O2.
- `process-item.ts`: `hasContent` is also true when `image_file_id` is set; `imageFileId` is
  passed through to `summarizeItem`.
- `webhook/route.ts`: a photo with no link is a valid capture (`tg://photo/<file_id>`,
  platform `other`, caption → note); a photo forwarded with a link sets `image_file_id` on
  that item too. Help text mentions screenshots.
- Tests: photo-size selection, the download (getFile/file failures, media type from
  extension), the `hasContent` rule, the image-block-before-text-block shape (SDK mocked),
  and the webhook's three new paths.

## Decisions
- Two lines beyond the letter of "process-item.ts: the hasContent line only" (plan §6.3):
  `imageFileId` is also passed into the `summarizeItem` call. Without it `hasContent` would
  correctly admit an image-only item past `needs_note`, but the image itself would never
  reach Claude — the feature would look done and do nothing. Both additions are marked
  `/* == S3 == */` and touch nothing else in the function.
- The webhook's `if (!text)` early-return became `if (!text && !photo)` — unavoidable, since
  a caption-less screenshot must not just get the "send me a link" reply.
- No dedupe check for the photo-only path beyond the existing `(chat_id, message_id)` unique
  index — there's no URL to look up (the pseudo-URL is generated from the file_id itself, so
  a genuine Telegram retry lands on the same row via the unique index either way).
- `TELEGRAM_BOT_TOKEN` was unset in this session, so `downloadTelegramPhoto` could not be
  exercised against the real Bot API — stated as untested-live per the exit criteria.

## Known issues
- **For S1:** `tg://photo/<file_id>` is not an http(s) URL. The current placeholder
  `items/[id]/page.tsx` renders `item.url` in an `<a href>` — it won't crash (React doesn't
  validate `href`), but it's a dead link. Render non-http urls as plain text.
- A photo-only item's platform is `other`, so `processItem` still calls `fetchPageMeta(tg://...)`
  before summarizing; `fetchPageMeta`'s existing try/catch swallows the failed fetch and
  returns nulls, so this is a wasted request, not a bug.
- `downloadTelegramPhoto` has no retry/timeout beyond `fetch`'s defaults; a slow Telegram CDN
  response extends the summarize call. Not worth adding for a single-user bot.

all green locally on the branch head; migration check clean (no schema touched). Live test
against the real bot: untested — no `TELEGRAM_BOT_TOKEN` available in this session.
