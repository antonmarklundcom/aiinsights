# O2 — Pipeline: webhook, processing contract, Claude call, cron

## Built
- `src/app/api/telegram/webhook/route.ts`: insert → reply → 200, with
  `processAndReply` moved into `after()` from `next/server`.
- Dedupe by cleaned `url` before inserting; the reply names the existing item and links to it.
- `webhook/pg-error.ts`: `isUniqueViolation` walks the `cause` chain for Postgres `23505`,
  so a Telegram retry is acknowledged silently instead of 500-ing.
- `src/app/api/cron/reprocess/route.ts`: bearer-auth GET, selects `pending`/`processing`
  with `attempts < 3` and `last_attempt_at` null or older than 10 min, 10 per run.
  `vercel.json` schedules it `*/15 * * * *`.
- `src/lib/process-item.ts` is now the processing contract: `processItem(id, { force? })`,
  `MAX_ATTEMPTS`, `MaxAttemptsError`, attempt claimed before any slow work, `ai_model` and
  token counts recorded on success, `needs_note` path unchanged.
- `src/lib/summarize.ts`: `claude-opus-5`, effort `low`, no `thinking`, `strict: true`,
  enum `category`, cached system block, 30,000-char transcript cap, English-only
  instruction, `fallbacks: "default"`, refusal → thrown error. Returns `{ output, usage }`.
- `src/lib/telegram.ts`: checks the response, logs Telegram's `description`, truncates at
  4,000 chars, declares `photo` on `TelegramUpdate` for S3.
  `src/lib/telegram-format.ts`: `formatReply` / `escapeHtml` / `formatDuplicateReply`.
- `drizzle/0002_damp_tyrannus.sql`: idempotent legacy-category mapping, then the cast to
  `item_category`. `src/lib/actions.ts` passes `force: true`. 41 new tests.

## Decisions
- **Two files outside `Owns`.** `vitest.config.mts` (new) — O1 recorded that without the
  `@/*` alias no test can `vi.mock("@/db")`, and O2's exit criteria require DB-mocked
  tests; it contains only the alias. `src/test/db-mock.ts` — `.returning()` added to the
  update chain, which `processItem` needs. Both are S2's to extend; neither was reshaped.
- `src/db/schema.ts` `category` → `itemCategoryEnum`. Not in `Owns`, but 0002 casts the
  column and CI fails on schema/migration drift, so leaving it `varchar` would break CI.
  O1's log hands this to O2 explicitly.
- 0002 was generated by drizzle-kit (so `meta/` stays in sync) and then hand-edited. Its
  first CASE arm passes through values that are already valid, which is what makes it
  idempotent and also preserves `design-or-ui` / `learning-resource` / `data-or-scraping`,
  which no legacy mapping rule produces.
- Secret and chat-id checks fail closed: unset config rejects rather than allows (§5.2).
- A bare note re-runs with `force: true` — the user supplying the missing note is exactly
  the case the attempt ceiling should not block. The cron never forces.
- `max_tokens: 16000` per the `claude-api` skill's non-streaming default; adaptive thinking
  is on by default on Opus 5 and its tokens count against the cap.
- `appBaseUrl()` reads `APP_URL` / `VERCEL_PROJECT_PRODUCTION_URL` from `process.env`
  directly, not `env.ts`: it is optional everywhere and must never block startup (§4.5).

## Known issues
- **Vercel plan:** `*/15 * * * *` needs a Pro plan. Hobby allows 2 cron jobs and runs each
  once per day, so on Hobby this schedule is not honoured — the retry loop would become
  daily. Confirm the plan, or widen `STUCK_AFTER_MS` to match a daily tick.
- **For S1:** `APP_URL` is undocumented in `.env.example` (O1's file). Without it, and
  outside Vercel, the duplicate reply drops its dashboard link rather than faking one.
- **For S2:** the config is `vitest.config.mts`, not the `vitest.config.ts` the phase table
  names — Vite's native loader warns on ESM syntax in a `.ts` config in a package with no
  `"type": "module"`. Extend that file; do not add a second one beside it. `db-mock` still
  does not interpret Drizzle conditions: the cron selection rule is asserted by rendering
  the recorded condition through `PgDialect().sqlToQuery`, worth lifting into `src/test/`.
- A Telegram retry of a message whose row was already inserted hits the URL-dedupe branch
  before the insert, so it answers "Already saved" rather than staying silent. That order is
  what plan §5.2 specifies; the silent path only covers a true insert race. Checking
  `(chat_id, message_id)` first would fix it at the cost of a second query.
- `usage` records `input_tokens` / `output_tokens` only. Once the system block starts
  hitting the cache, `cache_read_input_tokens` is not counted anywhere, so the dashboard's
  cost figure will read low. Plan §2 has no column for it.
- The webhook's `after()` callback cannot be awaited in production, so a failure inside it
  is only visible via the item's `status`/`processing_error` and the Telegram reply.
- The cron route sets `maxDuration = 300` and works through its batch sequentially. If the
  deployment caps functions lower, the run is killed part-way — acceptable, because each
  item's attempt is claimed before its slow work, so the next tick resumes rather than
  repeats.
- No database was reachable (§4.15): 0002 is verified by review and by a clean
  `drizzle-kit generate`, not by being applied. Its idempotency guards are untested against
  a real Postgres.
- `attempts` is claimed with a non-atomic read-then-write, so two concurrent runs on the
  same item (cron tick racing a manual retry) could both see the same count. Single-user
  app; not worth a transaction.

## Adversarial re-read (plan §4.10)
Three findings on the branch, fixed in one commit before merge: the cron ordered
`last_attempt_at asc`, which sorts NULLs last in Postgres and starved never-attempted items
behind older retries (now `asc nulls first`); `truncateForTelegram` cut at a fixed offset and
could split an HTML tag, which makes Telegram reject the whole message rather than shorten it
(now cuts on a line boundary, with a partial-tag trim as the fallback); and the two notes
above about retry wording and uncounted cache tokens were recorded rather than changed.
